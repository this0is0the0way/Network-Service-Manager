# Network Service Manager v2.5.4

## Название проекта и интерфейса

Публичное название проекта и репозитория — **Network Service Manager**.

В консольном интерфейсе намеренно сохранено имя **BESKAR**. Поэтому при запуске
`NetworkManager.ps1`, в заголовке программы, встроенной справке и некоторых
внутренних именах (например, `BESKAR_YYYY-MM.log`) по-прежнему может
отображаться `BESKAR`. Это часть интерфейса и не является названием GitHub-проекта.

------------------------------------------------------------------------

## Назначение

Network Service Manager --- инженерная утилита для быстрого переключения
сетевых настроек при ПНР и сервисных работах.

Программа поддерживает:

-   VLAN + статический IPv4;
-   статический IPv4 без VLAN;
-   несколько временных IPv4 на одном адаптере;
-   временные маршруты;
-   Mixed-профили;
-   возврат DHCP/DNS;
-   восстановление исходного состояния;
-   автоматическую адаптацию под разные USB--Ethernet-драйверы;
-   темы интерфейса;
-   добавление и редактирование IP-профилей через интерфейс;
-   ручную проверку связи через `ping`;
-   автоматическую проверку `PingTarget`;
-   управление отображением `DeviceName`;
-   журналирование операций.

## Запуск

Рекомендуемый вариант --- ярлык на PowerShell с включённым «Запуск от
имени администратора».

Также можно использовать `Start.bat`.

### Создание ярлыка

На рабочем столе:

``` text
Правой кнопкой мыши → Создать → Ярлык
```

В поле «Расположение объекта»:

``` text
C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe -NoLogo -NoProfile -ExecutionPolicy Bypass -File "D:\ПУТЬ\К\Network-Service-Manager\NetworkManager.ps1"
```

Укажите рабочую папку Network Service Manager и включите:

``` text
Свойства ярлыка → Дополнительно → Запуск от имени администратора
```

Права администратора необходимы для изменения VLAN, IPv4, DHCP,
маршрутов и расширенных свойств сетевого адаптера.

## Команды

В главном меню можно вводить номер профиля или команду.

### `ping`

Ручная проверка доступности узла:

``` text
ping
```

Программа запросит адрес.

Можно сразу указать адрес:

``` text
ping 192.168.218.2
```

Поддерживается IP-адрес или имя узла.

Параметры ручного ping:

``` powershell
$PingCount = 2
$PingTimeout = 500
```

Для проверки используется стандартный Windows `ping.exe`.

### `pingtarget`

Управляет автоматической проверкой адреса `PingTarget` после применения
профиля.

Команда находится в `help`, но не выводится в нижней строке быстрого
доступа главного меню, поскольку используется не постоянно.

``` text
pingtarget
```

Меню:

``` text
Настройка автоматической проверки связи

PingTarget позволяет после применения профиля
проверять доступность адреса, указанного в профиле.

Текущее состояние: ВКЛ

1. Включить проверку
2. Выключить проверку
0. Назад
```

`PingTarget` хранится внутри конкретного сетевого профиля.

### Автоматическая проверка PingTarget

После применения профиля:

``` text
Применение профиля
        ↓
Ожидание восстановления сети
        ↓
Попытка 1/5
        ↓
Ответ получен → проверка завершена
        ↓
Нет ответа → следующая попытка
```

Если ответ получен на первой попытке, остальные попытки не выполняются.

Настройки:

``` powershell
$PingDelayAfterApply = 5000
$PingRetryCount = 5
$PingRetryDelay = 1000
```

Для автоматической проверки используется `ping.exe`. Это обеспечивает
совместимость с Windows PowerShell 5.1, где `Test-Connection` может не
поддерживать параметр `-TimeoutSeconds`.

Важно: если профиль применён, но `PingTarget` не отвечает, это не
означает автоматически, что профиль применён неправильно. Устройство
может быть выключено или связь может отсутствовать по другой причине.

### `devicename`

Управляет отображением необязательного поля `DeviceName` при применении
профиля.

``` text
devicename
```

Меню:

``` text
Настройка отображения DeviceName

DeviceName — необязательное поле профиля.
Оно позволяет показывать название подключаемого устройства
при применении сетевого профиля.

Текущее состояние: ВКЛ

1. Включить отображение
2. Выключить отображение
0. Назад
```

Команда `devicename` находится в `help`, но не добавляется в строку
быстрого доступа главного меню.

Само значение `DeviceName` по-прежнему редактируется через `edit`.

### `edit`

Редактирование существующего профиля:

``` text
edit
```

или:

``` text
edit 3
```

Можно изменить:

-   название;
-   категорию;
-   VLAN;
-   IP;
-   маску;
-   шлюз;
-   `DeviceName`;
-   `PingTarget`.

Перед сохранением показывается состояние «Было / Стало».

### Остальные команды

-   `add ip` --- создать новый сетевой профиль через мастер;
-   `theme` --- изменить оформление;
-   `objects` --- вернуться к выбору объектов;
-   `adapter` --- выбрать другой сетевой адаптер;
-   `dhcp` --- снять VLAN/статику и включить DHCP;
-   `state` --- обновить состояние;
-   `reboot` --- полностью перезапустить программу;
-   `help` --- открыть справку;
-   `exit` / `quit` --- выход.

-   `91` --- выбрать другой адаптер;
-   `97` --- восстановить исходное состояние;
-   `99` --- вернуть VLAN «отсутствует» и DHCP;
-   `0` --- назад к выбору объектов из меню профилей.

## Объекты и профили

Начиная с версии 2.4.0 профили разделены по объектам.

``` text
Network-Service-Manager
│
├── NetworkManager.ps1
├── Theme.json
├── AdapterProfiles.json
│
└── Profiles
    ├── Объект №1.json
    ├── Объект №2.json
    └── Объект №3.json
```

Каждый JSON в `Profiles` считается отдельным объектом. Имя файла без
расширения отображается в меню.

Внутри объекта:

``` text
0 → назад к выбору объектов
```

Создание объекта выполняется через меню объектов. Новый объект может
быть создан и непосредственно во время `add ip`.

При изменении объекта создаётся резервная копия:

``` text
Profiles\<Объект>.json.bak
```

## Добавление IP-профиля

Введите:

``` text
add ip
```

Сначала мастер предлагает режим: `Network`, `MultiAddress`, `Routes` или
`Mixed`. Набор полей зависит от выбранного режима. Для `Network` он
последовательно запрашивает название, категорию, VLAN, IP, маску, шлюз и
дополнительные поля.

`exit` или `cancel` на любом шаге отменяют создание без сохранения. Это же
работает при вводе имени нового объекта.

Категория — это подпись, по которой профили группируются в списке текущего
объекта. Она не меняет IP, VLAN, маршруты и настройки адаптера. Например:
`ПНР`, `Сервис` или `Сетевые профили`.

`Enter` в поле VLAN означает отсутствие VLAN. `Enter` в поле маски задаёт
`255.255.255.0`; маску также можно указать как `255.255.255.0`, `/24` или
`24`.

`VLAN: null` и отсутствие поля `VLAN` означают одно и то же: ранее
установленный VLAN должен быть снят.

Дополнительные поля:

``` json
"DeviceName": "МИП + Scada",
"PingTarget": "192.168.218.2"
```

## Автоматическая адаптация VLAN

Список физических адаптеров и свойства выбранного драйвера проверяются при
каждом возврате в главное меню и перед применением профиля, возвратом DHCP
или восстановлением снимка. Пока консоль ожидает ввод, фонового опроса нет.
После отключения, переименования или замены выбранного адаптера требуется
выбрать его заново. Замена проверяется по `InterfaceGuid`, а не только по имени.

`AdapterProfiles.json` хранит результаты обнаружения. Сохранённая запись не
подменяет текущее чтение драйвера, в том числе если ранее было записано
`SupportsVlan: true` или `DisableMethod: Unknown`.

`Packet Priority & VLAN` / `*PriorityVLANTag` — переключатель обработки тегов,
а не номер VLAN. Скрытый параметр вроде `IntelANSVlanID` без отображаемого
поля VLAN ID сам по себе не подтверждает возможность прямой настройки.
В такой записи `SupportsVlan: false` означает, что текущий способ управления
VLAN через расширенные свойства не подтверждён; это не оценка возможностей
самого сетевого контроллера.

При переходе на профиль без VLAN пустое значение не требует сброса. Если
найдено непустое значение и драйвер не сообщает подтверждённый способ его
отключения, операция останавливается. Ошибка чтения свойств также останавливает
операцию: она не считается доказательством отсутствия VLAN.

Программа перечитывает реальные свойства выбранного драйвера и ищет
числовой VLAN-параметр.

Поддерживаются, в частности:

``` text
VLAN_ID
RegVlanID
VlanID
VLANID
*VlanID
```

При этом `AdapterProfiles.json` используется как кэш, а не как
единственный источник истины.

Например, один адаптер может использовать:

``` text
VLAN drv: VLAN_ID
```

а другой:

``` text
VLAN drv: RegVlanID
```

Оба варианта должны обрабатываться автоматически.

------------------------------------------------------------------------

## VLAN → без VLAN

При переходе с профиля с VLAN на профиль без VLAN программа сначала снимает
текущий VLAN и проверяет результат.

Только после успешного подтверждения снятия VLAN назначаются новые
IPv4-настройки.

Если VLAN не удалось снять, применение профиля останавливается, а IP не
считается успешно применённым.

## APIPA 169.254.x.x

Windows может автоматически назначить служебный адрес:

``` text
169.254.x.x/16
```

BESKAR не удаляет его и не изменяет сетевой стек Windows.

Для удобства он скрывается только в строке `IPv4` интерфейса BESKAR.

## Рекомендации

-   перед первым применением новой версии держите копию предыдущей;
-   новые VLAN-драйверы сначала проверяйте на одном профиле;
-   при странном поведении адаптера можно удалить `AdapterProfiles.json`
    или очистить его до `[]` для чистого анализа;
-   не закрывайте программу во время изменения VLAN;
-   для MultiAddress не задавайте несколько шлюзов по умолчанию без
    необходимости;
-   после применения VLAN-профиля проверяйте состояние адаптера и
    результат PingTarget;
-   если `PingTarget` отключён, профиль всё равно применяется обычным
    образом.

## Чистая базовая сборка v2.5.4

Эта версия является базовой точкой для дальнейшей разработки Network Service Manager.

Структура чистой сборки:

```text
Network-Service-Manager_v2.5.4
├── NetworkManager.ps1
├── Start.bat
├── README.md
├── CHANGELOG.txt
└── RELEASE_MANIFEST.txt
```

Пользовательские и машинозависимые файлы не входят в базовую сборку.

### Файлы, которые создаются/используются во время работы

```text
Profiles\
AdapterProfiles.json
OriginalNetworkState.json
Theme.json
Logs\
StartupError.log
```

#### `Profiles\`

Содержит JSON-файлы объектов и их резервные копии. Это пользовательские данные и они не входят в чистую базу.

#### `AdapterProfiles.json`

Кэш/память сведений о сетевых адаптерах. Не переносится между компьютерами как обязательный файл.

#### `OriginalNetworkState.json`

Снимок исходного сетевого состояния конкретного компьютера. Не переносится в чистую сборку.

#### `Theme.json`

Пользовательская тема. Если файла нет, программа использует встроенные настройки интерфейса. После сохранения темы программа создаёт `Theme.json`.

#### `Logs\`

Рабочие журналы программы.

#### `StartupError.log`

Создаётся при критической ошибке запуска.

### Старые файлы

Следующие файлы относятся к предыдущей архитектуре и в текущей версии не используются:

```text
NetworkProfiles.legacy.json
NetworkProfiles_резерв.json
```

Они намеренно исключены из чистой сборки.

**От этой сборки Network Service Manager v2.5.4 в дальнейшем считаем текущий `NetworkManager.ps1` единственной базой исходного кода.**
